# 工程報告的白話寫法

寫給要修改文件的工程師與要看結果的主管。讓人讀懂現況、原因與下一個動作；可信度來自來源與準確的限制，語氣保持直接、平實。

此寫法參考使用者指定的 `E:/BackUp/Git_EE/Enumd-private-vault/.agents/skills/human-writing/SKILL.md`（1.2.0）、`references/reality.md`、`references/formats.md` 與 `references/revision.md`，整理於 2026-10-02。只採用通用寫作與事實保留原則，沒有讀取日記、建立個人畫像或轉入私人事實。使用本 skill 不需要存取 vault。

## 起筆先有材料

先分清正式要求、公司文件的記載、已核實的實際紀錄、審查者推論與目前未知。每個重要事實能回查固定來源；文件自述已測試，寫成「文件記載已測試」，沒有執行紀錄就不能直接改成產品已通過。

材料不足就保留缺口並縮短說明，不編例子、不補造執行過程、核准人、期限或工程師的想法。報告長度跟已找到的材料走，不為了湊兩三頁反覆講同一結論。

## 讓讀者早點知道要做什麼

摘要第一段直接說本次範圍、已成立的結果與最重要的限制。每個修正項先指具體檔案／段落與目前問題，再給修改動作及完成條件。SHA、digest、完整行號與逐題推理留在技術層。

一段處理一件事。下一段增加新事實、必要解釋或動作，刪掉只換詞重述的段落。保留有用的原因與適用條件，避免每句都塞「可能」「或許」「無法確認」；真正會改變讀者行動的未知，放在相關項目附近。

用具體主語與動詞。寫「將威脅模型的 Windows 加密實作改成和需求文件一致」，比「完成產品安全治理一致性的優化」容易執行。這是句型示意，實際改法仍依本次來源，不預填技術選擇。

## 用字與句子

- 採繁體中文與工程師常用詞。第一次出現的重要術語用一句白話說明，Task ID、正式標準名及必要技術名稱保留。
- 主語與動作先出現，原因與條件接在後面。長句確有必要可以保留，讀兩次才懂就拆開；避免整篇都像口號短句。
- 直接說判斷與依據，不預告「接下來從三個面向分析」，不立一個讀者沒有的誤解再推翻。
- 不用賦能、抓手、治理閉環、全面完善之類空話。工程上的「對齊版本」「追溯引用」有明確對象時可以用，不能只剩抽象名詞。
- 不為了像人增加「我親眼看過」、假對話、情緒、粗口、錯字或戲劇化比喻。
- 一件事說完就停，不在末段重新摘要全文或強加升華。交付連結與必要 gate 說明依 repo contract 保留。

## 固定格式優先保留

這是有契約的工程報告。主管摘要四章、A／B／C、六欄表、Task 15 欄與 Action 八欄照模板，不套用論壇長文格式。

一般說明文字避免提示性冒號、裝飾破折號與翻案套句。**固定欄位標籤、STATUS、Task／Action 標題分隔、路徑、網址、程式碼、原始證據與必要條件**可保留格式需要的標點。不得為了散文禁則改壞 parser、追蹤 ID、否定條件或原文。這依 human-writing 的「具體文體覆蓋通用寫法」及本次使用者指定交付形式調整。

官方／公司原文要精確保留的引用，不為文風刪改；另寫白話解釋。固定 claim boundary 中必要的否定要留下，不把「不能證明已執行」修成「可以進行發布」。

## 資料定稿前做一次保真修文

1. 讀摘要與每個「要怎麼改」，確認工程師第一次看就能知道對象與動作。
2. 刪除同義重複、空泛建議、名詞堆疊與無來源例子；每段保留它實際增加的訊息。
3. 核對修文前後的文件位置、數字、版本、Task／Action ID、verdict、strength、authority、basis、狀態與適用條件。
4. 原來屬於文件記載、推論、待確認或待補的資訊，沒有被改成已核實／已完成。Cannot Claim 與來源保留。
5. 結構化流程在既有 authoring 文字欄位完成修文，固定資料後才產 Markdown 與 HTML；不改生成 Markdown。舊人工報告則先修來源 Markdown，再以舊入口轉 HTML。兩者都檢查畫面與來源一致。

vault 的 `check_prose.py` 是通用散文提示工具，本 skill 不將它直接用作整份結構化 SSDLC 報告的 gate。固定欄位與技術引用可能包含它會標示的字樣；先人工判斷語境，不能為清警告刪掉證據或聲稱自動檢查已證明「像人寫」。
