# S1 Assessment 報告呈現規則

版本：1.5｜2026-10-02｜repo-local analysis and reporting rule

## 1. 適用範圍與權威

本 repo 的所有 AI agent 在分析、撰寫或更新 **S1 文件覆蓋 assessment、Pilot 結果及產品文件補充審閱**時，必須先讀本規則，按 §7 分析，再從共用模板產出報告。相同來源與依據沿用相同欄位、分類及既有判定規則，不能每次自行設計另一套。

「用這個 branch 再 review」「重新分析 SSDLC 文件」「更新 Pilot 報告」都適用；不用等使用者再次提醒要三份報告。先核對分支、固定來源及既有報告，再完成同一套交付。單純詢問概念或解釋舊結果，不觸發新的 assessment。

判定仍以既有 [REPORT-1 rubric](s1-assessment-reporting-rubric.md) 及 S0／S1 contract 為準。本規則不改 verdict、basis、evidence strength、queue、assessment schema 或既有 Review Engine 輸出，也不授權重新判定、更新機器 assessment 或啟動 S2。§11 的 HTML 只提供三層人類報告的閱讀入口。

一般對話、AI Governance 更新報告及其他 artifact 仍沿用各自的 contract，不強套本格式。

## 2. 固定交付三層，依讀者需要往下查

| 層次 | 讀者與用途 | 內容 |
| --- | --- | --- |
| 主管摘要 | 主管與一般讀者先了解結果 | 文件範圍、Task 覆蓋、執行證據、核准狀態與主要問題。 |
| 工程師修正單 | 工程師直接開始修訂或補證 | 六欄 Action List，分成 A 改文件、B 補證據、C 改善建議。 |
| 技術審閱附錄 | 審查者查證「為什麼要改」 | 逐份分析、完整 NIST 判定、規則依據、條件及驗證軌跡。 |

- 使用[主管摘要模板](../../templates/s1-assessment-summary.md)、[工程師修正單模板](../../templates/s1-assessment-actions.md)與[完整技術附錄模板](../../templates/s1-assessment-technical-review.md)，填入本次事實；不得自行更名或重排固定章節及欄位。已有技術附錄時保留其原章節與證據，補齊必要內容，不為套模板刪除舊理由。
- 同一個評估輸出目錄中，主管摘要用 `<report-id>-summary.md`、工程師修正單用 `<report-id>-actions.md`、新建技術附錄用 `<report-id>-technical-review.md`。`report-id` 沿用該次評估的識別，不每次另起名稱。
- 已有完整報告就保留原檔名及歷史引用，改定位為技術附錄，補上返回主報告的連結；不為了簡化而刪掉證據。
- 三層必須有導覽連結，並對應同一份來源範圍、固定版本與判定；每個 Action ID 連到附錄的完整依據。既有 manifest／metadata 保留在技術層，不新增一份競爭的 assessment。
- 新範圍的補充報告可共用導覽，但不得覆寫舊範圍結果，或沿用不相符的 digest。

閱讀入口與最終回覆的連結標籤固定為：**主管摘要、工程師六欄修正單、完整技術附錄**。分支／版本可以改變來源與輸出位置，不能改變這三層的用途、固定欄位及交付要求。目錄中的檔名以既有 report-id 為準；不要為同次評估反覆換名。

## 3. 主管摘要固定骨架

標題後先放報告狀態、日期及一句核心結論。若結果仍待人工接受，或人工判讀尚未同步 machine assessment，必須醒目標示 **STATUS: HUMAN REVIEW DRAFT**；尚未同步時，說明機器版保留舊結果。

接著只用下列四個二級章節，順序與標題固定：

1. `結論`：參考基準、文件份數與範圍、Task 覆蓋結果、實際執行證據強度、核准狀態及一句主要發現。
2. `工程師要處理什麼`：摘要 A／B／C 類數量或主題，直接連到工程師修正單，不先展開逐題 NIST 證明。
3. `建議處理順序`：先確認產品／Release／Design baseline，再修文件內容與引用，接著回查真實測試／Release／Risk evidence；另有直接 coverage gap 時依其影響調整優先序並說明理由。
4. `詳細 NIST 判定`：連到技術附錄及既有 manifest／metadata，說明人工／機器狀態與本次停止點。

主管摘要以 **2–3 頁內的閱讀量**為目標，可以更短，不是固定 PDF 頁數保證。工程師修正單是直接工作入口；逐題 NIST 表格、證明、完整清單及技術資料留在附錄。不得反覆重述結論或要求工程師先讀 NIST reasoning 才能找到改法。

白話問題與重點可以按 Task 改寫，但 Task ID、原 verdict、證據強度和審查狀態必須從本次 assessment／人工審閱紀錄取得，不能照範例預填為 COVERED 或 weak，也不能把其中一項自動換算成另一項。

## 4. 用語與宣稱限制

- **COVERED** 固定解釋為「在本次範圍內，文件已涵蓋該題要求」。不得寫成「已落實」「已測試通過」或加上表示工作完成的勾選圖示。
- **Evidence Strength** 指實際執行的證據強度；核准狀態另行說明。不得因草稿就自動降級，或因寫得詳細就自動升級。
- **未辨識到已核准文件** 必須限定本次來源；不得改寫成「公司沒有正式規範」。
- **未找到證據** 必須限定搜尋範圍；不得改寫成「從未執行」或「其他地方不存在」。
- **人工審閱建議** 不等於正式接受、風險接受或產品放行；主報告與附錄須保留相同狀態。
- 白話問題要問文件的要求、安排或記載；不得把「有沒有定義測試」寫成「測試是否完成」。
- 改判或範圍擴大時，主報告用一句話交代；完整 Previous／Reassessed、理由及受影響來源留在附錄。
- 七題 Pilot 結果不能外推公司所有產品或完整 SSDF，也不能換算未定義分母的合規百分比。
- 原始碼版本首次用白話解釋；SHA-256、manifest／corpus digest、行號、basis 逐項歸屬及完整 cannot_claim 清單放附錄。主報告仍須留下影響讀者結論的限制。
- `basis` 只沿用 `nist_normative`、`local_derived_guidance`、`reviewer_inference`；不得另縮寫成 `local_guidance`，或把 company source 當成第四種值。

參考基準的溝通分工固定為 **NIST SSDF＝要做什麼、OWASP SAMM＝成熟到哪、ISO／IEC＝管理／標準化**。這個分工不取代正式要求，也不讓三者互相排斥。要做 SAMM 或 ISO／IEC 評估時，另指定模型／標準、版本、條文及範圍；沒有評估就不能給成熟度分數或符合性結論。

## 5. 附錄必須保留什麼

附錄保留範圍與固定版本、各文件分析、跨文件觀察、驗證紀錄及來源指紋。單題 finding 的欄位及順序依 [REPORT-1 §8](s1-assessment-reporting-rubric.md#8-單題報告用這個順序寫)，包含來源、判定理由、獨立審查建議與 Cannot Claim；不得為了縮短主報告而刪除。

Task Coverage Gap 與 Improvement Opportunity 必須分開；NIST 正式要求、公司條文與審查者推論必須分開。保留既有五種 verdict、三種 basis 及各維度獨立性，不另造摘要專用狀態。

manifest／metadata／assessment 等機器資料沿用既有 contract。檔案成員或 digest 檢查不代表逐字引文、行號、語意判定或實際執行已被驗證。

## 6. 工程師必須看得出要改哪裡

工程師修正單的三個二級章節固定為 `A. 文件要修改`、`B. 證據要補`、`C. 改善建議`。每張表只用以下六欄，名稱及順序固定：

| ID | 類型 | 哪裡有問題 | 現在的問題 | 要怎麼改 | 怎樣算改完 |
| --- | --- | --- | --- | --- | --- |
| 穩定 ID，連到技術附錄 | 具體問題性質 | 產品、檔案 ID／路徑與段落 | 已觀察到的缺漏或不一致 | 具體修改或真實紀錄的補入方式 | 能回查的對照與完成條件 |

- **A 文件要修改**：政策／需求的直接 coverage gap、內容不一致、缺欄或引用問題；須有規則與來源支持。列入 A 不自動降低 coverage。
- **B 證據要補**：要求已有定義，但真實執行、發布或風險決策尚不可回查。先找既有受控紀錄，補 traceability；不能靠重寫報告、勾選或推填結果宣稱完成。
- **C 改善建議**：不影響目前 Task coverage 的可選改善，與 A／B 分開。主報告須明說不以它降低判定；具體門禁是否受其他規範影響留在附錄，不能由 C 一概宣稱全部不阻擋。

各類沒有項目時明寫「本次未列」，不造出問題或建議湊數。所有可交付工程師的項目都在修正單列出，不把 E-06 等必要補證藏到附錄才看得到。

每個 Action 必須能完成以下句型；補證項可寫「請在某報告補上真實紀錄的受控引用」，仍須指到檔案及段落：

> 請修改 ___ 文件的 ___ 段落，因為目前 ___；改成／補上 ___；完成後用 ___ 確認。

寫不出具體位置、改法或完成確認，就先留在技術附錄的待釐清觀察，不派給工程師。不得寫「SSDLC 管理應更加完善」之類無法執行的工作；保留原 finding 與 UNRESOLVED 等狀態，不把未釐清誤報成沒有問題。

報告不能只停在 verdict 或「待確認」。每個 Action 的完整理由與條件，必須在技術附錄用固定順序回答：

| 欄位 | 必須寫清楚 |
| --- | --- |
| 問題編號與性質 | 沿用該份報告的穩定編號；屬於 Task coverage gap、文件內容／一致性問題、執行證據待補或改善建議。未確認時明寫待確認。 |
| 文件與位置 | 完整路徑、章節／條文 ID；行號輔助定位，綁定既有固定版本。 |
| 規則依據與效力 | 具體要求及來源；分清 NIST 正式要求、公司規則、草稿要求與本地審閱期待。 |
| 目前哪裡有問題 | 規則要求什麼，文件目前寫什麼、缺什麼或互相不一致在哪裡；區分觀察與推論。 |
| 要修改或補什麼 | 指定哪個段落／欄位要更新、補入哪些已核實資料或紀錄；不能只寫「加強管理」「補齊證據」。 |
| 完成確認方式 | 修改後怎樣回查與對照；實際執行／核准仍須相應紀錄，不能用填完表格代替。 |
| 適用條件與待確認事項 | 例如尚未準備發布、設計基準未定或來源在本次範圍外；不能臆測負責人、期限、版本或核准。 |
| 對判定的影響與不能宣稱 | 是否直接影響原 Task verdict；依既有理由判斷，不因列入修訂清單就自動降級或宣稱已修好。 |

這些是人類報告欄位及問題性質，不新增 machine schema、verdict 或 queue 狀態。

只有能指出適用要求與直接不符合事實，才能寫「未符合該要求」。公司來源仍為草稿時，寫「相對於公司草稿要求的文件缺漏／不一致」，不能宣稱違反已生效規範。草稿中的測試門檻不能改寫成 NIST 必做條件。

沒有執行紀錄時寫「證據待補」，不直接推論未執行。沒有既有規則支持的補欄建議，標為審閱期待或改善建議，不冒充必做要求。文件尚在撰寫時可保留待辦；不得為了完成修訂清單而填入假版本、測試結果、勾選或核准。

確實沒有問題時明寫「本次範圍內未發現具體問題」；沒有項目數配額，不能造出缺口。摘要可只說主要主題，修正單保留所有可執行項，完整理由保留在附錄。

## 7. 每個 agent 固定採用的分析流程

1. **先固定基準與來源**：確認 NIST 版本、Task 範圍、來源 commit／manifest、文件核准狀態及尚未讀到的範圍。沿用既有記錄，不假設公司規則已生效。
2. **逐題對照**：把正式 Task 要求、公司條文、實際找到的內容及審查者推論分開；依 REPORT-1 區分 coverage gap 與 improvement，獨立保存既有各評估維度。
3. **找出具體工程問題**：對照產品文件之間的版本、內容、引用與可回查紀錄。文件存在或文字完整，不能直接推出已執行。
4. **轉成 A／B／C 工作**：A 指明要改的段落；B 指明要找的真實紀錄及補在哪裡；C 只放可選改善。找不到適用要求時，不硬判成違規。
5. **套句型檢查**：每項必須寫得出 §6 的修訂句型。不能通過的先留待釐清，不丟給工程師，也不刪掉原觀察。
6. **交付三層報告**：用共用模板整理主管摘要及六欄修正單，附上完整判定與來源；核對三層數字、ID、結果、條件及宣稱限制一致，再依 §11 產出網頁閱讀版。

首次審閱、換分支重審、加入新文件及純文字整理，均先辨識本次工作類型。純格式整理沿用已記錄的判定；重審依使用者授權與新來源逐題核對，不照抄上一輪 verdict。未讀內容必須說清楚，不能用 diff 審閱冒充全部文件全文重讀。

核心成功條件是：**分析負責辨識有來源支持的問題，報告把問題翻譯成工程師可執行、可確認的修改或補證工作。** 相同規則不保證不同 agent 的語意判讀完全相同；若判讀不同，保留理由與來源交由審查，不靜默改判。

## 8. 每次交付前的人工核對

1. 摘要使用四個固定章節，修正單使用 A／B／C 與六個固定欄位，三層及每個 Action 的附錄依據可以跳轉。
2. 份數、版本、Task ID、verdict、證據強度與範圍限制和附錄一致。
3. 已交代文件核准狀態、人工／機器結果關係及本次尚未證明的事。
4. 未刪除附錄的既有證據，也未把整理報告當成重新判定或執行驗證。
5. 每個修訂項目都能完成 §6 句型並回答「哪份文件、哪條規則、什麼問題、要改什麼、怎樣確認」；證據缺口與違反規則的結論沒有混用。

預設交付網頁時，另依 §11 確認畫面、篩選、問題詳情及來源版本；網頁不取代上述五項核對。

這五項是報告交付的必要檢查，不是可選提醒。任何一項未完成，先修正報告；若因來源或其他明確 blocker 無法完成，交代已完成／未完成部分，不宣稱完整報告已交付。人工審閱草稿可以完成交付，但仍須保留待接受及機器未同步的狀態。

這是 agent 的撰寫規則及人工 review 清單，沒有新增 validator、hook 或 CI enforcement。章節與連結檢查通過，只能證明呈現結構；不能證明語意正確或讀者已接受。

## 9. 重審時固定保存版本與追蹤問題

1. 先從既有 manifest／metadata／附錄取得上一輪 report-id、來源 commit、範圍與問題 ID；不要用工作目錄目前的檔案數猜測舊範圍。
2. 同一來源版本及範圍的文字／格式整理，沿用現有三份檔名與 report-id，保留判定、證據及歷史引用。判定理由的實質改變必須明寫，不當作純格式整理。
3. 來源 commit 或納入範圍變更，建立一組新版本報告及相應來源綁定。先沿用已建立的版本目錄；尚未建立時，在原報告目錄的 `revisions/<commit前7碼>-<corpus_digest前8碼>/` 保存三份報告，保留原 report-id／檔名。名稱撞到不同來源時延長指紋，不覆寫。新 Pilot 沿用自己的評估目錄，不強行套用 `report-2`。
4. 每組報告須有同一個 report-id、來源版本、範圍、Task 數、verdict、evidence strength、核准狀態及 A／B／C 分類。主管摘要說重點，附錄存完整資料；必要的問題不得只藏在附錄。
5. 上次問題沿用穩定 ID，逐項記錄延續、部分改善、已解決或本輪未重現及支持理由。新問題才用新 ID。改名、整併、刪除文件或佔位文字消失，都不自動等於問題解決。
6. 文件 coverage、文件 review 意見、真實執行證據、風險接受、發布核准及 machine assessment 同步分開。格式規則本身不授權改公司文件、補造執行結果、更新 machine assessment、commit／push 或執行 S2。

既有 `report-2-product-documents-review.md` 及 `branch-16/` 等歷史路徑保留，不追溯搬移。它們可作寫作版型參考，不能照抄其份數、日期、verdict、證據強度或修正項目。

## 10. 每次完成回覆都列出三個閱讀入口

先用白話說本次最重要的結果，再以固定順序列出三個實際檔案連結：

```markdown
1. [主管摘要](本次主管摘要的完整路徑)
2. [工程師六欄修正單](本次工程師修正單的完整路徑)
3. [完整技術附錄](本次完整技術附錄的完整路徑)
```

連結必須指向本次來源版本的檔案，不能把上一輪連結當成本次交付。寫檔完成後核對連結與 Action 錨點，刪除模板提示及未填標記，並交代草稿／接受／機器同步狀態。驗證資訊留在附錄或回覆的 `驗證` 中。

有網頁閱讀版時，先附「網頁報告」連結，接著保留上述三個來源入口；HTML 是同一份報告的閱讀方式，不是第四份獨立 assessment。

只有三份檔案存在、必要內容齊備且 §8 核對完成，才可說「三層報告已交付」。只列 findings、只回覆 verdict、只寫摘要、只給計畫或只說會照做，都未達交付條件。缺來源時如實報未完成，不製造空報告假裝交付。使用者明確縮小交付範圍時依其指示，說明哪些層未產出，不宣稱完整三層交付。

## 11. 網頁閱讀版使用同一套來源與版型

每次新 assessment 或分支重審，預設產出三層 Markdown 與 `<report-id>-report.html`，使用 [HTML 共用模板](../../templates/s1-assessment-web.html)。已有 REPORT-3B 合約資料時，使用 [skill 助手](../../.agents/skills/ssdlc-assessment-report/scripts/workflow.py) 的 `project` 依序呼叫既有 Markdown／HTML generator；舊人工 Markdown 用 `render` 與[原 reader](../../tools/generate_assessment_web.py)。使用者明確縮小交付時依其指示，不因此重判或自動 migration。

結構化流程在既有 authoring 文字欄位完成保真修文並固定資料後，才生成 Markdown；不再手改生成檔。預覽後仍需修文字時建立新資料版本，重新驗證、產出，不借用舊接受／同步紀錄或只改 digest 繞過來源綁定。

網頁固定提供主管摘要、工程師六欄修正單、完整技術附錄三個入口。工程師可搜尋問題、按產品／範圍及 A／B／C 篩選，點選穩定問題 ID 查看 §6 的八項完整依據，再跳至附錄。產品篩選只是閱讀分類，不能推成正式適用性判定；優先級只沿用報告明列的值，不由 Task verdict 換算。

- **來源固定**：舊人工流程由同目錄三份 Markdown 與既有 corpus metadata 產出。結構化流程依 REPORT-3B 的已驗證資料與 lifecycle 產出三份 Markdown，再用 exact-byte binding 轉 HTML；metadata 保留於固定資料根目錄，不為版面搬移或手填。三份 report-id／狀態、完整 commit／digest 與當次來源一致。
- **同版本交付**：結構化版本目錄的 `markdown/` 保存三份生成檔，`reading/` 保存逐位元相同的三份來源與 HTML。來源相對連結必須有效；HTML 階段失敗時保留已完成 Markdown，回報 partial 與非零 exit code，不宣稱完整交付。舊人工模式沿用同目錄布局。
- **內容保留**：沿用當次 Task verdict、evidence strength、A／B／C、Action ID、修訂內容、條件、核准狀態與 Cannot Claim。空分類寫本次未列，不能照抄範例數量或預填 COVERED／weak。Markdown 附錄與既有 manifest／metadata 保留。
- **離線閱讀**：單一 HTML 內含樣式與閱讀操作，不使用 CDN、外部字型、網路請求或結果寫回。原始報告下載與附錄的來源連結是讀者自行點選。工程處理狀態、核准或證據不能由網頁操作改成完成。
- **保留版本**：沿用 §9 的報告目錄、識別及歷史。頁面明示來源版本與人類報告狀態，保留四個輸入檔案指紋。產出工具檢查格式與來源綁定，不證明語意推論、逐字引文、實際執行或審閱接受。
- **交付核對**：在瀏覽器確認桌面／手機內容可讀、搜尋及分類結果正確、問題詳情八欄完整、返回／附錄跳轉可用；畫面份數、Task 與 Action 和來源一致。若網頁產出失敗，保留來源與既有網頁並交代原因，不宣稱網頁已更新。

固定命令如下，檔名換成本次實際來源；既有技術附錄可以保留原名：

```powershell
python -X utf8 tools/generate_assessment_web.py --summary <目錄>/<report-id>-summary.md --actions <目錄>/<report-id>-actions.md --technical <目錄>/<report-id>-technical-review.md --metadata <目錄>/<既有-corpus-metadata>.json --output <目錄>/<report-id>-report.html
```

缺 metadata 或固定來源資訊時先補足真實的來源綁定，不猜造 digest。上述 legacy 轉換器只讀既有人類報告，不接入 `assessment.yaml → Review Engine`，不為轉網頁自動移植 REPORT-3B 結構化資料或開始 S2；已有結構化資料時，使用本節前述 REPORT-4 固定入口。外部架站、公開分享及部署另依使用者授權；本規則只要求本地可開啟的報告。
